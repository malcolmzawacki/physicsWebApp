# Implementation audit — 2026-09-14

**Historical audit:** Corrections are documented in [September audit corrections](implementation_fixes_2026-09-14.md). The findings below describe the checkout before those corrections.

Reviewed the current checkout at `cad9009`, including the routed site, shared UI, generators, and `xtrct_docs`. The working tree was clean before this audit. No implementation changes were made.

This is a list of issues identified by source inspection and targeted execution, not a guarantee that every random case, browser interaction, or printed layout is correct. P1 means incorrect physics or a significant broken workflow; P2 means a functional defect or important compatibility gap; P3 means a lower-impact inconsistency. Portability gaps are explicitly separated from failures in current activities.

## Current activity and export defects

1. **[P1] The parallel schematic does not represent the circuit being graded.** In [the parallel renderer](C:/Dev/Python/physicsWebApp/app_pages/1_3.5_Current_Electricity_Series_Parallel.py:61), the final `pop()` restores the drawing position to the top of R2, then the return wire starts there. Inspecting actual Schemdraw element coordinates gives battery terminals at y=0 and y=3, resistor ends at y=0, and the return rail at y=1. There is a wire-only path between the battery terminals, while the resistor bottoms do not connect to the return rail. Both parallel activities nevertheless grade using ideal parallel-resistor equations. Connect both branch bottoms to a common rail at the battery return terminal, and remove the wire from the upper R2 node.

2. **[P1] Medium/hard tension answers violate force balance.** [TensionGenerator](C:/Dev/Python/physicsWebApp/utils/generators/forces/tension_generator.py:51) applies the opposite wire's vertical sign to each denominator term. For opposite vertical directions, the resulting vertical wire force is `-mg`, rather than `+mg`. Reproduction: `random.seed(0); TensionGenerator().tension_scenario('Hard')` gives mass 29 kg, angles 54°/6°, directions up-right/down-left, and tensions approximately -388.10/-229.37 N. Their horizontal resultant is zero but their vertical resultant is -290 N; +290 N is required. The random geometry also needs a feasibility constraint so both string tensions are positive. This affects the site and the hard questions in the default `funny_forces_practice` worksheet. The boolean denominator guard also does not independently test both denominators or near-zero values.

3. **[P1] Thermal losses can exceed the available energy and produce complex answers.** [The thermal number builders](C:/Dev/Python/physicsWebApp/utils/generators/energy/thermal_loss.py:44) use an inclusive upper bound `energy // 2 + 2`, which can exceed small initial energies. A reproduced hard Elastic ↔ Kinetic problem has a 4 kg object at 1 m/s (2 J), loses 3 J, and asks for compression of a 2 N/m spring. Its stored answer is approximately `1j`. Reproduction: seed Python random with 6, then call each type in `ThermalLossGenerator().stored_metadata()` in order at Hard difficulty. Bound losses by the available energy and validate real, finite physical outputs; the same sampling pattern exists in several builders in this file.

4. **[P2] Static-incline questions are underdetermined.** [Both branches](C:/Dev/Python/physicsWebApp/utils/generators/forces/incline_generator.py:76) describe an object merely “at rest” but use `mu_s = tan(theta)` as an equality. Rest only requires `mu_s >= tan(theta)`. Asking for the coefficient requires “minimum coefficient”; asking for the angle requires “maximum angle” or an explicit impending-slip condition. This affects the site and multiple default forces-worksheet questions.

5. **[P2] Hard induction asks for a charge magnitude unsupported by the given information.** [The induction model](C:/Dev/Python/physicsWebApp/utils/generators/static_electricity/induction_model.py:32) sets transferred charge chunks equal to the rod's charge chunks. [The page](C:/Dev/Python/physicsWebApp/app_pages/1_3.3_Static_Electricity_Induction.py:188) grades those exact magnitudes, but its stated rule only describes redistribution without touching; it does not disclose this numerical classroom convention. Induced magnitude is not determined by rod charge alone. Either explicitly define the invented chunk-transfer rule, supply an appropriate quantitative model, or ask only for signs and mechanisms.

6. **[P2] A standard-page canceled countdown cannot resume, and feedback disappears on rerun.** [Interface scoring](C:/Dev/Python/physicsWebApp/utils/ui.py:384) renders feedback and calls the shared countdown only within the new-submission branch. After a correct Constant Motion answer with cancellation enabled, unchecking the checkbox reruns the page: the question ID stays unchanged, success feedback disappears, and the countdown checkbox disappears. The saved `submitted=True` also prevents submitting again from restarting it. The countdown component itself works; the caller must persist feedback and render the pending countdown on subsequent reruns, as Relative Motion already does. Incorrect feedback likewise disappears on unrelated reruns.

7. **[P2] Choice selections carry into a new question.** [Question storage](C:/Dev/Python/physicsWebApp/utils/ui.py:167) resets `submitted` but not `user_answers_selected`; the choice renderer resets selections only when the answer count changes. Reproduced on Types of Motion Graphs: selecting Positive, then clicking New Question, leaves `['Positive', None]` selected on the new problem. Clear selections with each new question ID, including manual and selector-triggered regeneration.

8. **[P2] Diagram matching can award repeat stars for one set.** [Check Match](C:/Dev/Python/physicsWebApp/utils/layouts/diagram_match_layout.py:76) increments stars on every correct click, without a per-question submitted guard. Cancellation keeps the same payload available for another award. Its activity-wide cancel key also carries cancellation between matching sets. Add a question identity and a recorded-attempt guard before adopting the shared countdown.

9. **[P2] Matching controls can describe a different exercise than the saved graphs.** [The matching lifecycle](C:/Dev/Python/physicsWebApp/utils/layouts/diagram_match_layout.py:33) only regenerates for a missing payload, explicit Generate button, or advancement. Switching Position-Time First to Velocity-Time First leaves the previous graph set on screen. Either regenerate on control changes or clearly distinguish pending generation settings from the currently displayed set.

10. **[P1] The documented dependency installation omits `python-docx`.** [requirements.txt](C:/Dev/Python/physicsWebApp/requirements.txt:1) does not declare it, while [document_creator](C:/Dev/Python/physicsWebApp/xtrct_docs/document_creator.py:1) imports `docx` immediately. [graph_utils](C:/Dev/Python/physicsWebApp/utils/graph_utils.py:2) also imports it, and MotionGraphGenerator imports that helper, so this reaches site motion-graph activities and the payload guardrail, not only exports. The existing local environment already contains the package and masks the fresh-install problem. Declare the dependency, or make document-only imports optional and declare a documented export dependency group.

11. **[P2] The Unit 1 preset cannot be passed to the document writer like the other presets.** [unit1_practice_doc](C:/Dev/Python/physicsWebApp/xtrct_docs/question_organizer.py:244) returns the generated list, whereas the other worksheet factories return a callable. `create_doc('Audit', Org().unit1_practice_doc(), 1)` raises `TypeError: 'list' object is not callable`. Return the factory consistently so multiple versions are independently generated. The existing organizer guardrail accepts both shapes and consequently hides the writer incompatibility.

12. **[P2] Enabling document diagrams crashes for ordinary site payloads.** [create_doc](C:/Dev/Python/physicsWebApp/xtrct_docs/document_creator.py:339) treats `diagram_data` as a ready-to-save figure, while most generators supply raw dicts/lists requiring `generate_diagram`. Reproduced with `create_doc('Audit', Org().funny_forces_practice(), 1, include_graphs=True)`: `AttributeError: 'dict' object has no attribute 'savefig'`. Constant-motion worksheets also contain displacement movement lists. Introduce an export adapter that renders raw data with its originating generator; do not infer that every `diagram_data` value is a Matplotlib figure.

13. **[P2] Export silently changes prompt structure and cannot render site Markdown/math.** [The writer](C:/Dev/Python/physicsWebApp/xtrct_docs/document_creator.py:335) collapses all whitespace, then assigns plain paragraph text. A reproduced displacement worksheet turns the numbered movement list and question into one run-on paragraph. Relative Motion's bold values and list formatting would print as literal Markdown if adapted for export; no math or markup conversion exists. Preserve meaningful paragraphs/list boundaries and define a print rendering contract before claiming general site-to-document compatibility.

## Shared-contract and cross-layout gaps

14. **[P2, portability] Mixed choice/text inputs cannot submit complete answers.** [Button fallback](C:/Dev/Python/physicsWebApp/utils/ui_components.py:143) and [dropdown fallback](C:/Dev/Python/physicsWebApp/utils/ui_components.py:167) display text fields but never copy their values into the submitted selection array. Any part without choices remains `None`. Merely copying a string is insufficient for numeric answers because button grading uses exact equality rather than numeric parsing/tolerance. No current activity failure was established for this mixed-control contract.

15. **[P2, portability] All dropdown questions are forced to use unique answers.** [Submission validation](C:/Dev/Python/physicsWebApp/utils/ui.py:355) rejects duplicates whenever input mode is dropdown, even for independent questions that legitimately share an answer. Uniqueness should be a ranking constraint, not a consequence of widget choice. Current ranking use can retain this constraint explicitly.

16. **[P2, portability] Normalization, storage, and rendering disagree about optional fields.** [Interface storage](C:/Dev/Python/physicsWebApp/utils/ui.py:186) drops normalized `extras` and only copies an explicit top-level allowlist. Worked explanations can be stored but are not displayed by the standard layout. Storage uses `timer`, feature lookup uses `time_limit`, and the actual countdown takes a layout argument; the choice path does not pass that argument. Separately, [normalization](C:/Dev/Python/physicsWebApp/utils/problem_payload.py:67) mutates a nonempty caller-owned extras dict when adding unknown keys. Preserve a normalized payload without mutating the input, and specify supported render features explicitly.

17. **[P2, portability] Equation metadata uses incompatible names and shapes.** [The equation helper](C:/Dev/Python/physicsWebApp/utils/ui_components.py:87) expects `honors_equation`/`conceptual_equation` from the generator, but `honors`/`conceptual` from the fallback dictionary. BaseGenerator returns stored metadata unchanged, and existing generators use the short keys. Current pages commonly mask this with a fallback; a metadata-inferred layout can show an empty equations panel. Relative Motion additionally adapts equation lists to a single LaTeX string. Normalize naming and value shape at one boundary.

18. **[P2, policy inconsistency] Parsing, grading, attempts, and advancement differ between layouts.** [Standard parsing](C:/Dev/Python/physicsWebApp/utils/ui.py:302) accepts `nan`/`inf` as parsed numbers and records them as wrong submissions, whereas Relative Motion rejects them. Standard numeric grading uses 10% relative tolerance and exact zero; circuits use `max(5%, 0.05)` in the displayed units. [Circuit submissions](C:/Dev/Python/physicsWebApp/app_pages/1_3.4_Current_Electricity_Circuits.py:199) and their series/parallel counterpart count each submission, including repeated wrong attempts, while Interface records only the first attempt. Circuits use a fixed sleep without the cancellation behavior available elsewhere. These differences need explicit product policy; they should not be silently unified if retry-based learning is intentional.

19. **[P2, portability] Document feature flags and payload contracts are incomplete.** [Side-by-side export](C:/Dev/Python/physicsWebApp/xtrct_docs/document_creator.py:341) renders graph/choice blocks regardless of `include_graphs=False`, while ordinary figures are omitted by default. Choice options outside that particular layout are not printed. The writer does not normalize payloads: multipart answer/unit mismatches are silently truncated by `zip`, while other missing fields fail later. Matching payloads (`prompt`, `correct_index`, option figures) and circuit cases (`prompt`, scalar `answer`, `unit`, diagram descriptions) also need explicit adapters before either the standard Interface or writer can consume them.

20. **[P2] Automated checks omit the failure boundaries above.** [CI](C:/Dev/Python/physicsWebApp/.github/workflows/correctness-guardrails.yml:1) runs two guardrails but neither interaction script. [The validator](C:/Dev/Python/physicsWebApp/tools/validate_payloads.py:109) registers only 11 generators, while this audit discovered 23 BaseGenerator subclasses. [The organizer check](C:/Dev/Python/physicsWebApp/tools/check_prompt_answer_consistency.py:406) checks problem dictionaries but never calls the document writer and explicitly tolerates the incompatible list-returning preset. The core payload validator checks structure, not real/finite numeric domains or physics. Add regression coverage at those boundaries, including circuit connectivity and actual export serialization.

## Lower-impact inconsistencies

- Star weights are derived from list positions, not named difficulty. A Medium-only activity such as Atwood earns one star, while Medium in a three-difficulty activity earns two. Progress identity also depends on display labels. See [give_stars](C:/Dev/Python/physicsWebApp/utils/ui.py:416). Define stable scoring weights and IDs if cross-activity comparison is intended.
- MotionGraphGenerator accepts difficulty but does not use it to change the generated graph distribution, while the UI awards different difficulty stars. See [choose_problem_dict](C:/Dev/Python/physicsWebApp/utils/generators/kinematics/motion_graph_generator.py:154).
- The document entry point uses sibling absolute imports, so script launch and package/module launch are not equivalent. See [doc_face](C:/Dev/Python/physicsWebApp/xtrct_docs/doc_face.py:1); standardize/document the supported invocation.
- The default forces preset repeats the kinetic-incline coefficient block; this appears to be a content-balance issue rather than an API failure. See [question organizer](C:/Dev/Python/physicsWebApp/xtrct_docs/question_organizer.py:127).
- Several earlier limitations are already acknowledged in `docs/compatibility_limits.md`; they remain present in the checkout. That document is not evidence of fixes.
